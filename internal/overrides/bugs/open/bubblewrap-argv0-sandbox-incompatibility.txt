Bubblewrap `--argv0` Sandbox Incompatibility
============================================

Status
------
Open.

Date Opened
-----------
2026-03-25T01:30:58-07:00

Scope
-----
This is not a TheKnowledge content bug. It is a local execution-environment
bug that materially impairs TheKnowledge maintenance because it breaks Codex's
sandboxed developer-tool paths on this host.

Summary
-------
Sandboxed Codex tool invocations fail on this machine because the local system
`bubblewrap` executable is version `0.6.3`, while the active Codex sandbox path
expects a `bubblewrap` interface that includes `--argv0`. When Codex tries to
run a non-escalated command through the Linux sandbox, the host binary exits
immediately with `bwrap: Unknown option --argv0`.

Symptoms
--------
- Non-escalated developer-tool commands fail before the requested shell
  command runs.
- `functions.apply_patch` is unusable in this environment because it depends on
  the same broken sandbox path.
- The same shell command succeeds when rerun with escalated permissions,
  showing that the shell command itself is not the problem.
- The failure pushes work toward escalated commands and full-file rewrite
  fallbacks, which slows workflow and weakens the normal safety ergonomics.

Live Reproduction From This Session
-----------------------------------
1. Non-escalated `pwd` failed immediately with:
   `bwrap: Unknown option --argv0`
2. The same `pwd` command succeeded when rerun with escalation and printed:
   `/home/mheck/codebase/HPG/actual/TheKnowledge`
3. Local host package information:
   - `/usr/bin/bwrap`
   - `bubblewrap 0.6.3`
   - `bubblewrap-0.6.3-1.el9.x86_64`
4. Local `bwrap --help` output lists many options but does not list `--argv0`.

Confirmed Local Evidence
------------------------
- The Codex launcher is `@openai/codex` version `0.116.0` installed under:
  `/home/mheck/.nvm/versions/node/v22.22.1/lib/node_modules/@openai/codex/`
- The package was installed or updated on 2026-03-24 at approximately
  `16:43:09 -0700`, based on the local `package.json` timestamps.
- The platform package selector in
  `/home/mheck/.nvm/versions/node/v22.22.1/lib/node_modules/@openai/codex/`
  `bin/codex.js` maps Linux x64 to `@openai/codex-linux-x64` and then resolves
  a vendored `vendor/x86_64-unknown-linux-musl/` tree.
- The vendored Linux Codex binary contains strings showing both:
  - explicit knowledge of `--argv0`; and
  - logic for system versus vendored bubblewrap.
- Relevant extracted strings from the vendored binary include:
  - `failed to exec system bubblewrap`
  - `Codex could not find system bubblewrap ... Codex will use the vendored`
    `bubblewrap in the meantime.`
  - `--argv0`
  - `--argv0 VALUE                Set argv[0] to the value VALUE before`
    `running the program`

What The Problem Is
-------------------
The failure is a host-tool compatibility mismatch between the Codex Linux
sandbox launcher and the system `bubblewrap` package shipped on this machine.
The sandbox launcher is attempting to invoke a bubblewrap feature that was not
available in the installed `0.6.3` binary. Because the command fails before
Codex can enter its normal sandboxed execution path, routine non-escalated
shell commands and patch operations abort at startup.

Why We Did Not Notice Earlier
-----------------------------
Two factors appear to be involved.

First, this exact failure mode only becomes visible when Codex actually uses a
non-escalated Linux sandbox path. In recent work we often proceeded through
approved escalated commands, which bypass this broken path, so the underlying
host mismatch was easy to miss.

Second, the locally installed Codex package appears to have been updated on
2026-03-24. That raises a plausible second explanation: a newer Codex build may
now rely on `--argv0` where an older build did not. That timing correlation is
real, but it is still an inference. This report does not yet prove the exact
Codex version boundary where `--argv0` became required.

In short: the strongest evidence is that we started exercising the broken
sandbox path more often, and the recent Codex upgrade may also have contributed.

Why Other Projects Are Not Complaining
--------------------------------------
This problem is environment-specific, not repository-specific.

- TheKnowledge itself did not create the mismatch.
- Any project on this same host could hit it if it exercises the same
  sandboxed Codex tool path.
- Many sessions will not expose it because approved escalated commands bypass
  the failing sandbox launcher.
- Many other users run newer distros, different operating systems, or
  different sandbox backends and therefore will not see this exact EL9/
  `bubblewrap 0.6.3` failure.

It is also not true that nobody is complaining about Codex sandbox behavior in
general. The public Codex issue tracker has multiple sandbox-related reports on
Linux, macOS, and WSL. Those reports are not all this exact bug, but they show
that sandbox/environment mismatches are a recurring class of problem rather
than an isolated local oddity.

Options
-------
1. Do nothing locally and keep using escalated-command fallbacks.
   Pros:
   - No system changes.
   - Lowest immediate operational risk.
   - Keeps all workarounds outside the repository.
   Cons:
   - Loses the ergonomics and safety of the normal sandboxed path.
   - Keeps `apply_patch` effectively broken here.
   - Adds friction and approval churn to normal maintenance work.

2. Add a user-local shim that strips `--argv0` before delegating to
   `/usr/bin/bwrap`.
   Pros:
   - Fast to test.
   - Can live entirely outside the repository.
   - Avoids system package replacement.
   Cons:
   - Potentially changes process behavior in subtle ways because `argv[0]`
     can matter to shell startup and mode detection.
   - Easy to forget, hard to support, and fragile across Codex updates.
   - Treat this as a debugging aid, not a clean fix.

3. Install a newer user-local `bubblewrap` and make Codex use it first on
   `PATH`.
   Pros:
   - Closest local match to what Codex appears to expect.
   - Keeps the workaround outside repository content.
   - Potentially restores the sandboxed workflow without waiting for upstream.
   Cons:
   - Introduces host-specific drift and maintenance burden.
   - Needs careful rollout so it does not accidentally affect unrelated tools.
   - Still a local workaround rather than a principled product fix.

4. Determine whether Codex can be configured to prefer its vendored
   `bubblewrap` instead of the system binary.
   Pros:
   - Uses the toolchain bundled with the installed Codex package.
   - Could avoid host-package drift if a supported switch exists.
   Cons:
   - This session confirmed the binary contains a vendored path and fallback
     strings, but it did not identify a documented user-facing switch for
     forcing that path.
   - Behavior remains partly inferential until verified in documentation or
     upstream code.

5. Pursue an upstream Codex fix.
   Pros:
   - Most principled long-term solution.
   - Could detect `bubblewrap` feature support or version before adding
     `--argv0`.
   - Could fall back automatically to vendored `bubblewrap` when the system
     binary is too old.
   - Would benefit other users on older enterprise Linux streams.
   Cons:
   - Requires upstream reporting, triage, and release time.
   - Does not unblock this host immediately.

Comparison
----------
Option 1 is the safest immediate posture but preserves the slowdown.
Option 2 is the quickest hack, but it is the least trustworthy because it
changes the command line in a way that may matter semantically.
Option 3 is the most practical local repair if we need relief soon and are
comfortable with a host-only workaround.
Option 4 could be better than Option 3 if Codex already supports it, but this
report does not yet prove the necessary switch or configuration.
Option 5 is the right product-level fix and should happen regardless of which
local workaround we choose.

Recommendation
--------------
Recommended near-term path:
1. Keep repository changes free of environment-specific hacks.
2. Continue using escalated fallbacks for urgent work on this host.
3. In parallel, test either a supported vendored-bubblewrap path or a newer
   user-local `bubblewrap` install outside the repository.
4. Report the bug upstream to Codex with the reproduction, local version data,
   and the fact that EL9 ships `bubblewrap 0.6.3` without `--argv0`.

Recommended strategic fix:
- Ask upstream Codex to detect bubblewrap capability or version before passing
  `--argv0`, or to fall back automatically to vendored bubblewrap when the
  system binary is too old.
