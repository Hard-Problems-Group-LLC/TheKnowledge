Full-Scope Black Validation Reformats Unrelated Tracked Files on Supported Interpreter
=======================================================================================

Status
------
Closed.

Date Closed
-----------
2026-03-27T12:38:45-07:00

Date Opened
-----------
2026-03-26T10:21:08-07:00

Scope
-----
This is a TheKnowledge repository-maintenance bug. It affects small,
otherwise scoped maintenance changes that try to clear the repository's
required full-scope `black` validation step.

Summary
-------
Once TheKnowledge's pinned `black==26.3.1` toolchain is run on a supported
Python interpreter, the required full-scope Black check does not clear
cleanly against the current repository baseline. Instead, it reformats a
large set of unrelated tracked files across `scripts/`, `tests/`, and
`standards-and-practices/dev-utils/security/`.

The result is validation spillover: a narrowly scoped change inherits a
repo-wide formatter sweep simply by attempting to satisfy the required Black
check.

Observed Reproduction From This Session
---------------------------------------
1. The active host default is Python 3.9.25, which could not install the
   pinned `black==26.3.1`. That separate toolchain drift is already tracked
   in `starter-validation-stack-drifts-from-supported-python-and-black-`
   `behavior.txt`.
2. A temporary Python 3.12 virtual environment under `/tmp/` successfully
   installed the repository's pinned dev toolchain, including
   `black==26.3.1`.
3. Running the required wrapped command with that supported toolchain:

   `PATH=/tmp/theknowledge-py312/bin:$PATH`
   `/tmp/theknowledge-py312/bin/python`
   `scripts/run_tool_with_timeout.py black`

   completed through the repository's one-file-at-a-time fallback path.
4. That run reformatted unrelated tracked files outside the debugging-knack
   changeset, including:
   - `scripts/codex_local.py`
   - `scripts/git_standard_commit_push.py`
   - `scripts/initial-setup.py`
   - `scripts/validate_knacks.py`
   - `standards-and-practices/dev-utils/security/entropy-check.py`
   - `tests/test_entropy_check.py`
   - `tests/test_run_tool_with_timeout.py`
   - `tests/test_windows_cli_shims.py`
   plus many additional files in the same areas.
5. Those unrelated formatter edits were restored immediately so the active
   changeset could remain scoped to the new debugging knack.

Impact
------
- Small documentation or test changes cannot clear the required `black`
  check without either accepting a broad unrelated formatting sweep or
  carrying a known validation exception.
- Review quality degrades because unrelated formatter churn obscures the
  actual change under review.
- Delivery slows down because every scoped task that attempts a full clean
  validation risks turning into a repository-wide normalization effort.

Why This Appears Distinct From Existing Black-Related Bugs
----------------------------------------------------------
This is not the same issue as the existing Codex sandbox asyncio wakeup bug,
which is about Black hanging on multi-file sandboxed runs. In this session,
the repository's serialized fallback path let Black complete one file at a
time.

This is also not the same issue as the existing starter-validation bug about
Python 3.9 incompatibility. That older bug prevented the pinned Black
version from being installed on the default interpreter. The current bug
appears after that blocker is worked around with a supported Python 3.12
environment.

Likely Root Cause
-----------------
The strongest current explanation is repository formatting baseline drift:
the tracked tree is not fully normalized to the currently pinned Black
release and its current parsing or target-version behavior.

Supporting signal from this session:
- Black repeatedly warned that Python 3.12 "cannot parse code formatted for
  Python 3.14," which suggests that the current formatter behavior and the
  repository's present baseline are not aligned cleanly on the supported
  runtime used here.

The exact final cause still needs confirmation, but the practical problem is
already clear: the required full-scope Black check is not presently a scoped
validation step for small changes.

Recommended Resolution
----------------------
1. Decide the canonical interpreter and target-version policy for Black in
   TheKnowledge's own validation environment.
2. Run one deliberate repository-wide formatting normalization changeset on
   that supported toolchain.
3. Treat subsequent small changes as exempt from absorbing unrelated Black
   churn until that normalization lands, while documenting the exception in
   completion notes.

Why This Matters
----------------
The repository requires disciplined, reviewable changes. A formatter
baseline that spills far beyond the active task undermines that goal and
makes the validation path noisier than the work itself.

Root Cause
----------
The pinned Black release was being run against a tracked repository baseline
that had not been deliberately normalized to that formatter behavior, and the
wrapper had no placement-driven Black policy to make the intended target
version and runtime explicit.

Resolution
----------
TheKnowledge now records Black target-version and runtime policy in
`tool_validation_profiles.json`, uses Git-first profile-driven discovery in
`scripts/run_tool_with_timeout.py`, and has completed one deliberate
repository-wide Black normalization pass on the supported Python 3.12
toolchain. The required Black check now clears against the updated tracked
baseline instead of forcing future scoped changes to absorb unrelated
formatter churn.
