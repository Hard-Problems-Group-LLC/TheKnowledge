Installation strategy
=====================

Use `install.sh` as the canonical POSIX bootstrap entry point. The shell
wrapper locates or installs a bootstrap Python 3.9+ interpreter, delegates
the main context work to `scripts/install-stage-2.py`, and then chooses one
of three scopes:
- default user-local standard install;
- explicit repo-local development or venv-only install; or
- explicit system-standard install with `--system`.
Development mode provisions the configured pyenv bootstrap/runtime selections
from `python-environments.json`, writes `.python-version`, refreshes the
repo-local `.venv`, and requires `direnv`. `bootstrap.sh`,
`bootstrap-stage2.py`, and `scripts/install_prerequisites.sh` remain
compatibility wrappers. For the broader interpreter and package-environment
precedence model that future multi-language bootstrap flows should follow, see
`standards-and-practices/docs/`
`Interpreters-and-Package-Management-Environments.md`.

Quick start
-----------

From the repository root:

```
./install.sh
```

That default is a user-local non-development install. Use development mode
when you want the pinned repo-local toolchain:

```
./install.sh --mode dev
```

Use `sudo ./install.sh --system` when you explicitly want a system-level
non-development install. Use `--mode venv-only` when you want only the
managed repo-local `.venv` and toolchain.

Supported platforms
-------------------

- Rocky Linux 9.6 (dnf/yum)
- Fedora 43 (dnf)
- Ubuntu 24.x (apt)
- Linux Mint (apt)
- Debian stable/testing (apt)
- Modern macOS releases (Homebrew)

What the installer does
-----------------------

- Detects the platform and chooses an available package manager.
- Installs `python3`, `venv` tooling, `git`, `curl`, and pyenv build
  dependencies when a bootstrap interpreter is missing and root access is
  available.
- Falls back to a user-scoped pyenv bootstrap when root access is not in use
  and a suitable interpreter is still missing.
- Uses standard mode as the default install mode.
- Installs standard mode into a user-local venv by default.
- Installs standard mode into system paths only when `--system` is present
  under root.
- Ensures the configured pyenv bootstrap and runtime selections exist,
  writes `.python-version`, and refreshes `.venv` only for development or
  venv-only repo-local modes.
- Delegates installation semantics to `scripts/install_project.py` when the
  consuming project provides that hook; otherwise uses the managed default
  Python-venv install behavior for development and standard mode.
- A consuming project's install hook may also publish or remove a
  project-bound developer launcher for development mode or manage the stable
  user/system launcher for standard mode.
- Installs or updates `direnv` and managed shell hooks only for development
  mode.
- Installs or updates managed git hooks only for repo-local development or
  venv-only mode when `scripts/install_git_hooks.py` is available in the
  repository or in a `TheKnowledge/` submodule.
- Installs or refreshes a managed `.gitignore` block in consuming projects so
  `.local/`, `.theknowledge-restricted-names.local`, and known local
  Codex/codex-wrangler artifacts stay ignored by default.

Notes and expectations
----------------------

- Run the installer from the repository root to ensure relative paths resolve
  correctly.
- Source `./set-context-bootstrap.sh` or `./set-context.sh` when you need to
  force one pyenv context explicitly. The tracked `.python-version` file
  makes the runtime context the default local choice.
- Keep project-local operator notes and similar AI guidance under
  `.local/ai-local-notes.md` or `.local/ai-local-notes.txt`. Those files are
  local-only policy inputs, not tracked starter payload.
- `sudo ./install.sh` without `--system` must fail with an explanation. Use
  `sudo` only for explicit system installs.
- `./install.sh --system` without root privileges must fail with an
  explanation.
- Running `./install.sh` directly as `root` without `--system` must ask for
  confirmation before doing a root-only user-local install. In
  non-interactive contexts it should abort instead.
- If the host lacks `sudo`, run `./install.sh` for a user-local install or
  install the required system packages manually before retrying
  `./install.sh --system`.
- `bootstrap.sh` and `bootstrap-stage2.py` remain valid compatibility entry
  points, but new docs and consuming-project guidance should prefer
  `./install.sh`.
- Entropy-secret checks are wired into managed hooks:
  - `pre-commit` runs entropy checks.
  - `pre-push` runs cached quality-gate checks.
  See `standards-and-practices/docs/security/entropy-checks.txt` for details
  and manual run commands.
- Standardized git operation utilities are available after setup:
  - `python scripts/git_standard_commit_push.py -m "<subject>"`
    Lists files about to stage, asks whether to review them unless
    `--assume-reviewed` is passed or prompts were disabled earlier in the
    current shell session, prefers Meld review when available as the
    default visual review path, runs `git diff` before its own
    staging steps, runs `git diff --cached` before commit, uses
    `project-management/state/pending-commit-changes.txt`
    as commit body text when that file is nonblank, and clears the queue
    after a successful local commit. Use `--resume-review-prompts` to
    re-enable prompts for the current shell session.
  - Operator shortcut: `ACP` means "add, commit, push." Treat it as a
    request to run the normal VCS workflow in meaningful commit-sized blocks,
    not as permission to make one monolithic commit or skip review and checks.
  - `python scripts/git_veteran_pull.py`
  - Cache file used by push quality gate:
    `.git/project-quality-cache.json` when a writable Git-backed cache path is
    available, or `.cache/project-quality-cache.json` otherwise
  - Runbook:
    `standards-and-practices/docs/security/git-tripwire-operations.txt`
- Consuming projects that update a TheKnowledge submodule should first fetch
  and briefly review the incoming upstream `trunk` delta in the submodule
  checkout. Prefer
  `python TheKnowledge/scripts/update_theknowledge_submodule.py`
  `--project-root . --knowledge-root TheKnowledge` for that workflow. The
  helper fetches,
  prints the incoming commit summary and diffstat, adopts the reviewed
  upstream commit, runs the managed drift report, refreshes the managed
  starter files when needed, and leaves a reviewable parent-repo diff.
- The managed starter for consuming projects also includes `install.sh`,
  `bootstrap.sh`, `scripts/install-stage-2.py`, `bootstrap-stage2.py`,
  `python-environments.json`, `.python-version`, `set-context.sh`,
  `set-context-bootstrap.sh`, `requirements-dev.txt`, `scripts/dev_setup.py`,
  `scripts/python_environment_bootstrap.py`,
  `scripts/tool_validation_profiles.py`, `tool_execution_constraints.json`,
  `tool_validation_profiles.json`, and `ECRs/TheKnowledge/` lifecycle
  scaffolding. That set installs the same pinned Black, Ruff, and pytest
  toolchain plus a default user-local standard install, explicit repo-local
  development mode with pinned pyenv selections and `.venv`,
  development-mode `direnv` integration, managed execution constraints,
  placement-driven runtime policy, and the standard local subtree for
  read-only upstream TheKnowledge requests.
- The managed drift report compares `AGENTS.md` sections plus those starter
  files. When it reports drift, refresh only the managed starter entries:
  `python TheKnowledge/scripts/initial-setup.py --project-root .`
  `--knowledge-root TheKnowledge --force --template .gitignore`
  `--template .python-version`
  `--template ECRs --template install.sh --template bootstrap.sh`
  `--template bootstrap-stage2.py --template python-environments.json`
  `--template requirements-dev.txt --template scripts`
  `--template scripts/install-stage-2.py`
  `--template scripts/python_environment_bootstrap.py`
  `--template scripts/tool_validation_profiles.py`
  `--template set-context-bootstrap.sh --template set-context.sh`
  `--template tool_execution_constraints.json`
  `--template tool_validation_profiles.json` and then review `git diff`
  before staging.
- To file TheKnowledge feedback from a consuming project, prefer
  `python TheKnowledge/scripts/send_theknowledge_feedback.py prepare`
  followed by `finish --message ...` in the active submodule checkout. Add
  `--push` only when the configured push URL is writable for the current
  operator.
- When the active TheKnowledge checkout is read-only and the request is not
  yet ready for upstream filing, draft it first under
  `ECRs/TheKnowledge/open/` in the consuming project. Move it to
  `ECRs/TheKnowledge/in-progress/` during active upstream handling and to
  `ECRs/TheKnowledge/closed/` once the upstream disposition is recorded.
  Compare resolved filenames against the writable TheKnowledge checkout's
  `internal/overrides/proposals/accepted-ecrs-list.md` when you need to
  confirm that one or more carried ECRs were accepted or implemented.
