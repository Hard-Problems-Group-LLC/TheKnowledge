Pinned Python Developer Tool Versions
=====================================

Scope
-----
Define the default pinned Python developer toolchain for TheKnowledge itself
and for consuming projects that adopt TheKnowledge's managed starter setup.

Problem Statement
-----------------
TheKnowledge currently defines Black, Ruff, and pytest with loose `>=`
constraints. Over time that lets formatter, linter, and test-runner behavior
drift across machines and across consuming projects. The resulting differences
make validation less reproducible and can introduce broad formatting churn
during otherwise narrow maintenance work.

Requirements
------------
- `pyproject.toml` must pin TheKnowledge's default Python developer tool
  versions exactly with `==`.
- The pinned default toolchain must include, at minimum, Black, Ruff, pytest,
  and `pytest-timeout`.
- The initial pinned versions are:
  - `black==26.3.1`
  - `ruff==0.15.7`
  - `pytest==9.0.2`
  - `pytest-timeout==2.4.0`
- `scripts/install-stage-2.py` must install the managed project in
  development mode with pinned tool dependencies, and those dependencies must
  resolve to the exact pinned versions above.
- `templates/requirements-dev.txt` must exist and must mirror the exact pinned
  dev-tool versions from `pyproject.toml`.
- `templates/scripts/dev_setup.py` must install the managed
  `requirements-dev.txt` into a local virtual environment, upgrading `pip`,
  `setuptools`, and `wheel` first.
- `tool_validation_profiles.json` must exist at the repository root and must
  define the managed steady-state Python tool runtime policy separately from
  the Python 3.9 bootstrap floor.
- `python-environments.json` must exist at the repository root and must
  define the bootstrap/runtime pyenv selections and their preferred base
  versions.
- `scripts/tool_validation_profiles.py` must exist and must expose the managed
  runtime-selection logic that consuming projects inherit with the starter.
- `scripts/ensure_theknowledge_tool_runtime.py` must exist for TheKnowledge's
  own direct-checkout maintenance path and must provision the pinned tooling
  under `.local/theknowledge-tool-runtime/` rather than borrowing another
  project's runtime.
- `install.sh`, `bootstrap.sh`, `scripts/install-stage-2.py`,
  `bootstrap-stage2.py`, `.python-version`, `set-context-bootstrap.sh`, and
  `set-context.sh` must exist at the repository root.
- `scripts/initial_setup.py` must install `requirements-dev.txt`,
  `scripts/dev_setup.py`, `scripts/tool_validation_profiles.py`,
  `scripts/python_environment_bootstrap.py`, `tool_validation_profiles.json`,
  `python-environments.json`, `install.sh`, `bootstrap.sh`,
  `scripts/install-stage-2.py`, `bootstrap-stage2.py`, `.python-version`,
  `set-context-bootstrap.sh`, and `set-context.sh` into consuming projects by
  default.
- `README.md` must explain that consuming projects receive starter toolchain
  files and may run `./install.sh` when they want the default pinned setup.
- `templates/README.md`, `templates/AGENTS-footer.md`, and
  `templates/project-management/git-flow.txt` must explain how the managed
  starter toolchain is refreshed in consuming projects.
- `standards-and-practices/docs/development-workflow.txt` and
  `standards-and-practices/docs/installation.txt` must explain how direct
  TheKnowledge maintenance and consuming-project starter bootstraps keep the
  toolchain pinned and reproducible.
- The starter-managed `.gitignore` block must ignore `.local/`,
  `.theknowledge-restricted-names.local`, and known local Codex artifacts so
  pinned-tool maintenance state and local policy inputs stay untracked.
- Tests must verify that:
  - the `pyproject.toml` dev dependencies remain exact pins;
  - `templates/requirements-dev.txt` stays in sync with those pins; and
  - `scripts/initial_setup.py` installs the managed starter toolchain files
    into consuming projects, including the runtime-profile policy files and
    the pyenv/bootstrap context files.

Non-Goals
---------
- Pinning every possible project runtime dependency that a consuming project
  might need for its own application code.
- Forcing mature consuming projects to abandon stricter or more specialized
  local bootstrap flows.
- Replacing project-local setup wrappers that intentionally extend the managed
  starter.
