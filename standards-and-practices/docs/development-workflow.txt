Development Workflow
====================

Start here to understand how work moves through the repository. Follow these
stages in order: propose, backlog, execute, and clear. Keep every change
traceable back to a proposal or explicit operator direction.

Some repositories define override record locations for their own live state.
When an override record map exists, use it instead of the default
`project-management/` paths shown below.

Proposals
---------

Use proposals to drive discussion before drafting a full specification. Follow
the template in `standards-and-practices/docs/format-for-proposals.txt` and
store each file in the matching status directory under
`project-management/proposals/` with a descriptive name. Use
`under-review/` while a proposal is awaiting a decision, then move the file
to `approved/`, `rejected/`, or `deferred/` as the status changes. Stamp
every proposal with an ISO 8601 date, status, and reviewer list. Keep the
status metadata aligned with the directory name. Cross-reference backlog
entries, bugs, and specifications in the metadata so readers can trace the
request through the workflow. Keep revisions append-only: update the status
and decision log instead of rewriting history, and record who approved,
rejected, or deferred the proposal.

Treat proposals as temporary while the team converges on scope. Move them into
their final status directory and capture the rationale in the decision log.
Once approved, draft the specification in
`standards-and-practices/docs/specifications/` before writing code or tests.
Reference the specification from the proposal so the
chain of custody stays obvious.

Backlogging
-----------

Convert approved proposals and direct operator requests into backlog entries.
Add new items to `project-management/backlog.txt` using the existing
asterisk-plus-blank-line formatting. Capture the requestor, a short actionable
summary, and an ISO 8601 timestamp showing when the item entered the queue.
Note blockers and dependencies inline so prioritization is transparent. Keep
the backlog ordered with the next item at the top. Move clarifying discussion
and partial findings into indented follow-up lines to avoid rewriting the
original request.

If the operator defers an item at this stage, move it to
`project-management/deferred.txt` using the deferral rules below so it can
return unchanged later. Retain the timestamp showing when it left the backlog
to preserve history.

Execution
---------

Promote an item to `project-management/tasks-in-progress.txt` when active work
begins. Copy the backlog entry verbatim, add a fresh timestamp for when the
effort started, and include current owners plus any known blockers. Link to
the relevant specification or proposal so reviewers can verify scope. While
executing, keep notes concise and dated.

Implement the specification, keeping code and tests aligned with Chicago style
documentation standards and the required checks. Run
`python scripts/run_tool_with_timeout.py black`,
`python scripts/run_tool_with_timeout.py ruff`,
`python scripts/run_tool_with_timeout.py compileall`, and
`python scripts/run_tool_with_timeout.py entropy_check`, and
`python scripts/run_tool_with_timeout.py entropy_tripwire_verify`, and
`python scripts/run_tool_with_timeout.py pytest` before declaring the work
ready. If progress stalls, move the entry back to the backlog with an
explanation and timestamp.

While work is in flight, append brief commit-ready summaries to
`project-management/state/pending-commit-changes.txt`. Keep the entries short
enough to serve as commit body text. The standardized commit/push helper uses
the nonblank contents of that file as the commit body and clears the file
after a successful local commit.

For substantive AI-driven development work, prefix intermediary
conversation updates with an inline bracketed ISO 8601 timestamp
including the timezone offset, for example
`[2026-03-25T01:05:12-07:00] Running full pytest.` Use timestamped
updates when work begins, before and after long-running commands or
waits, and at major phase boundaries. Include elapsed durations when
they are easy to compute. Use this conversation timeline for
workflow profiling instead of relying on hidden logs.

For broad exploratory smoke runs, avoid ad hoc shell snippets. Implement
repeatable checks as formal tests or reusable scripts under
`standards-and-practices/dev-utils/`, and document usage in
`standards-and-practices/docs/testing/` so they can be rerun consistently.

The managed pre-commit hook installed by setup scripts runs
`entropy_check` automatically. Keep that hook installed on developer machines
and CI-adjacent sandboxes where commits are authored.

Keep the Python toolchain reproducible. In TheKnowledge itself, rerun
`./install.sh` when the pinned toolchain drifts or when `install.sh`,
`scripts/install-stage-2.py`, `python-environments.json`,
`.python-version`, or the runtime-policy helpers change. `./bootstrap.sh`
and `./scripts/install_prerequisites.sh` remain compatibility wrappers. In
consuming projects that adopt the managed starter bootstrap, rerun
`./install.sh` after the starter bootstrap/runtime files,
`requirements-dev.txt`, `tool_validation_profiles.json`, or
`scripts/tool_validation_profiles.py` change, or when the local tool
versions drift. The bootstrap entry point may still run on the bootstrap
Python floor while creating the steady-state developer-tool environment with
the managed runtime policy.

If `tool_execution_constraints.json` marks a tool-and-environment
combination unsafe to parallelize, follow the recorded workaround. In a
matched Codex sandbox, run Black only through
`python scripts/run_tool_with_timeout.py black`; the harness will fall back
to exactly one file at a time when Black would otherwise hit the known
multi-file hang, and `black -W 1` is not sufficient. If another file-safe
formatter or linter still hangs inside a Codex sandbox on a multi-file run,
retry the explicit file list one file at a time. Keep that workaround narrow
to explicit file lists or other clearly file-safe modes, and rerun the full
required checks outside the affected sandbox or in CI before clearing the
work.

For standardized git operations, use:
- Before any `git add`, list the files about to be staged and ask whether to
  review them.
- Offer `1` review at least one file in the changeset, `2` proceed without
  review for this changeset, and `3` proceed and suppress review prompts for
  the rest of the current session until they are resumed.
- If review is requested, prefer changeset review in Meld when
  available as the default visual review path.
- Launch `meld .` from the repository or submodule root so Meld opens its
  version-control view for the full working tree.
- If Meld version-control view is unavailable or unsuitable, compare a
  temporary clean snapshot directory against the working tree in Meld's
  folder-comparison mode.
- Otherwise offer file-by-file review in the conversation or abort the
  staging step.
- Never infer a Git author or committer email address from commit history,
  hostnames, remote URLs, network overlays, or similar context.
- Require a deliberate identity before commit. Prefer configured
  `git config user.name` and `git config user.email`; explicit
  `GIT_COMMITTER_*` and optional separate `GIT_AUTHOR_*` overrides are also
  valid when set intentionally.
- If a separate author identity is not configured, reuse the explicit
  committer identity for author instead of inventing another address.
- Run `git diff` before any `git add` and `git diff --cached` before any
  commit.
- `python scripts/git_standard_commit_push.py -m "<subject>"` for commits and
  pushes with mandatory cached quality gate checks (including entropy
  tripwire verification). The helper lists files about to stage, asks for
  review unless `--assume-reviewed` is passed or prompts were disabled
  earlier in the current shell session, rejects commits whose
  author/committer identity is not explicitly configured, consumes
  `project-management/state/pending-commit-changes.txt` as commit body text
  when that file is nonblank, and clears it after a successful local commit.
  Use `--resume-review-prompts` to re-enable prompts for the current shell
  session.
- `python scripts/git_veteran_pull.py` for guarded fast-forward pull updates.
See `standards-and-practices/docs/security/git-tripwire-operations.txt` for
failure diagnostics and maintenance guidance.

The default quality-gate cache file is `.git/project-quality-cache.json`.
Delete it or pass `--no-quality-cache` through the commit/push script when a
full uncached rerun is required.

Clearing
--------

When work finishes, move the item to `project-management/completed-tasks.txt`
and place it at the top of the file. Preserve the asterisk-plus-blank-line
formatting and include a concise summary of what shipped, the date it landed,
and who completed it. Note how any blockers were cleared and reference merged
commits, specifications, or proposals for traceability. If the operator defers
the work instead of clearing it, follow the deferral process below to retain
the original request for future reactivation.

Before clearing, confirm the corresponding specification is complete, the
required checks have passed, and reviewers can trace the change back to the
proposal and backlog entries. If a follow-on task is needed, open a fresh
backlog entry rather than rewriting the completed record.

Deferrals
---------

When the operator requests that a feature be deferred, move the item from
`project-management/backlog.txt` or `project-management/tasks-in-progress.txt`
into `project-management/deferred.txt` without changing the ordering or the
asterisk-plus-blank-line formatting. Add a short note that explains why the
work is pausing and stamp the entry with an ISO 8601 timestamp to show when
the deferral occurred.

Preserve the original task language exactly so it can be re-enabled. Insert a
quoted block immediately under the rationale and timestamp. Start the block
with a line that reads `>>BEGIN>>`, end it with a line that reads `>>END>>`,
and prefix *every* line of the original text—including blank lines—with `> `.
If the item is reactivated later, remove the deferral entry and copy the
quoted content back into the backlog or in-progress list verbatim.

Status Hygiene
--------------

Keep backlog entries concise, actionable, and timestamped when they enter the
list. Only promote items to `project-management/tasks-in-progress.txt` when
work begins, and return them to the backlog if progress stops. For completed
work, record the outcome in `project-management/completed-tasks.txt` at the
top of the file with a timestamp and a brief summary of what changed.

Ensure every stage leaves a paper trail: proposals record decisions, backlog
entries show queue position, in-progress tasks log active ownership, and the
completed list reflects what shipped. Avoid rewriting history; append concise
notes instead.
